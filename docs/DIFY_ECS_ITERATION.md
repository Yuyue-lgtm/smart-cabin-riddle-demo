# 阿里云 Dify 测试与正式发布

后续日常迭代集中在同一套阿里云 Dify 1.17.1。Cloud 保留历史资料与只读排查，不再作为日常维护目标。实例映射见 [environments.json](../dify/environments.json)；真实资源是否已经初始化，以其中 `alibaba-test` 和 `alibaba_test_apps_created` 为准。

## 使用方式

| 场景 | 应用 | 知识库 |
| --- | --- | --- |
| 本地 Demo | 三套阿里云测试应用 | 独立测试经验库 |
| cabinplay.xyz | 原三套阿里云正式应用 | 当前正式经验库 |
| Dify Cloud | 历史来源备份 | 历史来源经验库 |

线上 Demo/Dify 均在 ECS 独立运行。Mac 关机、关闭阿里云客户端不会停止线上网站。只有本地联调、管理和发布时才需要维护通道。

维护入口已改为 Mac 后台管理的直接 SSH 隧道，不再依赖阿里云客户端的8081/2222转发。Dify 管理地址仍为 `http://127.0.0.1:8081/apps`。安装、自动重连、完整链路检查及网络变化边界见 [连接与诊断](DIFY_CONNECTION.md)。

## 一次性初始化

工具依赖位于 `tools/dify-workflow-mcp`；缺失时在该目录执行 `npm ci`。项目根目录运行：

```sh
node tools/dify.mjs login
node tools/dify.mjs setup
```

`login` 打开仅本机监听的登录表单，使用阿里云 Dify 的账号密码。密码只用于当前登录，不保存。会话写入被 Git 忽略的 `tools/dify-workflow-mcp/.env.ecs`，权限600，读取时自动刷新；Cloud 原维护会话使用另一文件，不混用。若会话被撤销，再运行一次登录命令，无需在聊天中传Cookie。

`setup` 会：

1. 读取三套正式应用发布图、草稿及完整无密钥 DSL；存在未发布正式改动则停止，先审阅这些改动。
2. 将真实备份写入新的 `dify/releases/<时间>-ecs-setup/`，保留历史迁移基线。
3. 复制独立测试知识库，检查全部有效分段、完整 JSON、处理规则和检索设置。
4. 复制三套测试应用，保持模型和业务图，改绑测试知识库；只发布测试副本并创建其独立服务端 Key。
5. 跑本地回归及测试草稿真实 BFF 回归，核对正式发布版未变化后，更新环境映射和 `.env.local`。

初始化过程的资源 ID 保存在私有 `tmp/dify-ecs/setup.json`，已经记录的资源会复用；异常时先检查日志，不删除知识库/应用后盲目重跑。Cloud 原 `.env.local` 只保存在私有 `tmp/dify-ecs/.env.cloud-backup`，不提交 Git。

## 日常本地迭代

```sh
node tools/dify.mjs dev
```

默认地址为 `http://127.0.0.1:4175/`。它使用 `.env.local` 的阿里云测试应用 ID 和 Key，同源 `/api/workflow` 代理转发至私有 Dify；浏览器不接触 Key。

4175 是新的浏览器来源，首次建立测试应用的独立会话，避免把先前 Cloud 的 conversation_id 发到新实例；在此来源中仍跨题、跨新局和刷新复用会话。旧4173进程若未重启，仍可能持有先前配置，请使用这次命令显示的地址。

在 Dify 工作室编辑带“测试 · ”前缀的应用，完成后发布测试应用，再通过本地 Demo 体验。API 调用使用已发布版本，不能只在控制台保存草稿就认为本地 Demo 已用上。知识库原文也先改测试库。

检查环境与回归：

```sh
node tools/dify.mjs status
node tools/dify.mjs test
node tools/dify.mjs verify
```

本地健康接口 `/api/health` 中的 `workflow_proxy.environment` 应为 `alibaba-test`，三个 App ID 应与环境映射的测试ID一致。`test` 运行本地 Node 回归及测试草稿的真实模型/BFF链路，使用独立虚构测试用户，不读取真实聊天。

`verify` 只在本地检查最新版本目录的文件清单与SHA-256，不需要转发或登录。版本目录还会自动保存知识库JSONL/Markdown原文与版本说明，不能只有一份临时文件或未经核对的导入模板。

## 正式上线

先生成只读备份和差异（不写正式草稿）：

```sh
node tools/dify.mjs release
```

确认测试体验与差异后，一条命令完成正式发布：

```sh
node tools/dify.mjs release --publish
```

发布命令重新读取当前版本并备份，核对测试草稿等于测试发布版、正式草稿等于正式发布版，然后依次执行：本地回归 → 测试应用真实回归 → 同步正式草稿 → 正式草稿真实回归 → 版本/知识库再次核对 → 发布并读回三套正式应用。

知识库内容或处理/检索设置变化时，先创建新的正式知识库版本并核对，原正式库保留；发布前不修改现有正式库。工作流将测试知识库引用映射到目标正式知识库。正式应用 ID 与 API Key 保持原样，因此只改 Dify 工作流不需要重启网站服务或换前端配置。

每次差异、备份、回归和发布进度写在对应 `dify/releases/<时间>-ecs/`。遇到并发编辑、格式/守卫不通过、知识库未索引或真实回归失败时停止；写过草稿的失败任务仅恢复仍属于本次发布的版本。部分发布失败时，会在没有并发修改的前提下恢复已经发布的旧版本。若通道断开无法确认回退，保留日志并人工核对，不能把失败说成发布成功。Dify 没有三应用统一事务，发布和回退也无法保证三个应用在同一毫秒切换。

本工具只发布 Dify 工作流/知识库，不负责把修改后的网页、BFF 代码上传 ECS。涉及接口结构或前端功能时，仍按网站 release 流程部署并验收。

## 验证边界

真实草稿回归通过当前 BFF 测试乘客问答、同会话续聊、环境分析与串词、P0不发言、入睡/醒来动作、参与邀请和提问预演。另直接运行实际绑定的经济索引检索节点，验证两个绑定ID与目标库一致并命中HK28。Dify通用hit-testing接口在此实例上会要求默认embedding模型，故此检查复用游戏已有检索节点，没有新增embedding模型或改变索引方式。情境分析可合法选择无需检索，不强迫每次参与事件都走检索。全部使用安全带、雨伞及虚构状态；云端模型调用会消耗额度。

首次完整发布已完成，版本 `2026-10-20T05-17-33-943Z-ecs`。测试应用/正式草稿各12次BFF请求及两次直接HK28检索通过，发布后公开BFF10次请求通过；真实备份、差异、发布图hash和运行ID均已保存到版本目录。业务图和知识库内容与此前正式版一致，未通过本轮修改产品规则。

历史已记录的“模糊换题属性问句沿用上一题语义”问题和HK10四/六题门槛矛盾没有借此次环境分离修复，仍需另做语义专项回归。通过结构化守卫或这些测试不表示所有自然语言语义都正确，也不替代完整浏览器流程验收。
